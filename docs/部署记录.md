# 首次部署与验证记录

日期：2026-10-13，时区：Asia/Shanghai。

本记录保存部署过程、遇到的问题、处理方法和验证范围。真实订阅、节点凭据、机场标识、服务器地址、SSH 配置、原始配置和未经脱敏的日志不属于公开交付物。

## 环境与配置核对

目标是一台 Ubuntu 24.04 x86_64 GPU 服务器。检查确认 Python、PyYAML、systemd 用户管理器可用，目标代理和控制端口没有占用。原先未安装 Mihomo，也没有自动代理环境变量。

从本机 Clash Verge 当前激活的配置中提取私有快照。核对订阅源与当前生效配置：117 个内置节点、28 个策略组、50 条业务规则、19 个规则集；节点、策略组、规则及规则集定义一致。本机的脚本与合并补丁没有增加实质性分流修改，因此每日刷新可以直接使用完整订阅。

快照只保存在仓库之外的私有目录，并通过 SSH 文件传输发送给服务器。公开仓库不包含这些快照。

## 安装过程

1. 从 Mihomo 官方 GitHub 发布页获取 `v1.19.32` 的 Linux amd64-compatible 压缩包，核对官方 SHA-256；解压后再核对传输到服务器的程序哈希。
2. 复用本机已有 GEO 数据和规则集缓存，通过离线初始化避免服务器首次启动时因无法直连下载站而失败；没有上传客户端数据库。
3. 配置用户目录中的 Mihomo。强制规则模式、代理监听 `127.0.0.1:7890`、控制 API 监听 `127.0.0.1:9090` 并使用随机密钥；关闭 TUN 和外部监听。
4. 保留源配置的节点、策略组和业务规则。原配置的 `off` 在 YAML 1.1 解析中被误读成布尔值，首次校验失败；改用兼容 YAML 1.2 布尔语义的安全解析器后校验通过，并加入回归测试。
5. 创建 `linux-clash.service` 用户级服务，启用异常退出后自动重启。创建每日订阅更新服务及定时器。
6. 为当前用户启用 Linger。该服务器允许用户自行启用，整个安装未使用 sudo。
7. 将自动代理环境加入登录配置和用户服务环境文件。自动加载片段位于 `.bashrc` 的非交互判断之前，新建 SSH 命令会话同样生效；原 shell 文件另存备份。
8. 设置每天北京时间 04:00～04:05 更新完整订阅。下载结果经过解析和 Mihomo 校验后才替换、热加载，保留最近一次工作配置；失败恢复行为使用虚构配置单独验证。

## 服务器网络适配

原规则集下载方式为直连，但部分 CDN 请求超时。为规则集下载指定原配置已有的主代理策略组，业务请求的 50 条分流规则保持原样。19 个规则集都完成了主动刷新；其中两项首次刷新失败，重试后成功，运行时均有非空规则内容。

初期还出现国内直连网站间歇失败。对照测试显示：同一服务器通过系统 DNS 直连百度成功，经原配置解析的代理入口请求失败，核心日志中出现 DNS 解析超时及部分目标连接超时。启用 `--direct-dns-system` 对应的私有设置后，已匹配直连的请求使用系统 DNS，代理请求继续沿用原解析配置。该适配在后续订阅刷新中自动应用。

这是运行环境适配，不是对上游业务规则的重写。工具默认保留上游 DNS；其他使用者按自己服务器的实测情况决定是否启用。

DNS 适配后的那轮 GitHub、Hugging Face 和百度请求均在首次尝试成功。初期部分站点和节点有过超时，测试命令最多尝试三次并明确显示每次重试；不能据此推断订阅未来始终稳定或所有网站/API 均可用。

为保留服务器正在进行的工作，没有重启整台服务器。开机启动结论来自 enabled 状态、用户管理器和 Linger 配置检查；实际验证了独立 SSH 会话、代理进程异常恢复和更新服务执行，没有把“配置完成”写成“整机重启实测”。
